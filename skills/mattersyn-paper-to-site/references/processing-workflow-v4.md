## Source sufficiency

Use the existing screened-pass local documents only. Read preparation sections, continuation paragraphs and the results needed to identify the product. Prefer existing source text, page renders and accepted evidence receipts. When a supplied main article refers to an available local SI for experimental details, inspect that SI before claiming the paper lacks a recipe. Verify its identity; do not assume a filename proves a match. Main/SI pairing is not a prerequisite to beginning assessment, and no new document acquisition is authorized.

A buildable contribution needs an identifiable material and inputs, an operational preparation with meaningful quantities and conditions, and an explicit connection to a reported structural outcome. Decide sufficiency for the actual method: an essential precursor charge, composition, thermal program or size-selecting condition can matter more than the number of filled fields. A missing optional unit cell, complete atomic coordinates, additional morphology image or ancillary measurement is not by itself a reason to skip a useful recipe. A substantial consolidation or annealing method may qualify with that specific scope; never describe it as an extraction of the upstream synthesis when that synthesis is absent.

Use three outcomes:

- **Eligible for regular integration:** sufficient preparation and product evidence exist; preserve all supported variants, then finish extraction, independent audit and shared material integration.
- **Skip: insufficient source information:** no usable preparation, essential preparation details are absent from the available source scope, or no recipe-to-structure assignment can be established. Save a concise private reason and exact source locators. Do not create a placeholder material page.
- **Technical or identity hold:** an unreadable file, parser limitation, missing local file, ambiguous document identity or unresolved evidence conflict prevents the decision. This does not establish that the paper lacks information and does not count as completed processing.

Do not omit known information to make a paper eligible or manufacture skip reasons to reach throughput. Conflicting reported measurements can be shown side by side when their source and specimen assignments are established. Keep unresolved assignments explicit.

## Work allocation and speed

Run source-scoped assessment/extraction and consolidated independent audits on different papers in parallel, with at most four workers including root and five active full-curation claims. Assessment batches can cover several papers without opening simultaneous full-curation claims. Root alone edits shared source/site repositories and publishes. Reuse unchanged passed scientific work, exact source bindings and shared illustrations. Correct software failures centrally; do not repeatedly rebuild a paper to repair unsupported unit syntax.

Use one successful full release build per ready batch, transport that artifact, reuse unchanged checks, and retain source/site CI, privacy and anonymous verification. Publish ready contributions without waiting for blocked ones. Skip insufficient papers promptly, with evidence, and move to the next existing screened source. Never slow an already accepted contribution merely to complete optional engineering elsewhere.

### Batch path to shorter publication cycles

Use one immutable baseline and one combined candidate for each ready batch. Before applying a batch, resolve final record, review, Reader, figure and asset-rights paths; run exact-key/schema checks and a single aggregate preflight over every delivered asset against the current policy. The preflight must include proposed source and site paths and identify all failures together. Fix the batch privately, rerun only the checks invalidated by those edits, and seal it once. Do not start a site build from a package whose declared assets or bindings are still provisional.

After sealing, run source CI and the one full site build in parallel when their inputs are independent. While those fixed inputs validate, authors can prepare the next private paper batch; they must not edit the sealed candidate. Once source CI passes, transport the existing built artifact, compare staged file hashes to that artifact, then publish. Do not rebuild or rerun the same release gate for an unchanged commit or artifact. A correction that changes scientific fields, sample/figure bindings, permissions or public bytes invalidates the dependent checks and requires a new immutable candidate.

For performance, measure paper-level timestamps for source decision, extraction ready, independent audit accepted, integration sealed, build, deployment and anonymous verification. Publish completed batches as soon as they pass all gates; do not wait for an arbitrary batch size or a blocked paper. A sustained rate of 20 live papers/hour requires an average publication cycle of three minutes per paper, or one verified 4-paper release every 12 minutes. Treat that as a measured capacity threshold, not a reason to weaken evidence review, merge distinct experiments, count skipped files or count a deployment before anonymous verification. If observed rates fall short, use the stage timings to target the slowest repeated handoff before requesting more compute.
